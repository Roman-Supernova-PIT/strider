# NERSC operational handoff — what made the v2 flat-z runs work

**Date:** 2026-08-02
**Source:** extracted from the working `strider-v2/nersc/*.sh` scripts that produced the
flat-z and 15-class models. This is the tacit knowledge that is not in any design
document — account, paths, environment quirks, and the two or three lines that quietly
prevented failures.

---

## 1. Reference card — the facts

### Slurm

```bash
#SBATCH --account=m4385
#SBATCH --constraint=gpu          # 'cpu' for conversion / audits
#SBATCH --qos=regular             # 'debug' for smoke (<=30 min), 'shared' for 1-GPU fractional
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --gpus=1                  # 1, NOT 4 - see 3.2
#SBATCH --cpus-per-task=10
#SBATCH --time=12:00:00
#SBATCH --mail-type=END,FAIL
#SBATCH --mail-user=mtdixon@hawaii.edu
#SBATCH --output=logs/<name>_%j.out
#SBATCH --error=logs/<name>_%j.err
```

The 15-class production model was trained with exactly this: **1 GPU, 10 CPUs, 12 h**.

### Filesystem layout

| what | where |
|---|---|
| Raw SNANA sims (read-only, project) | `/global/cfs/cdirs/m4385/snana_roman_root/sims/` |

## 2. The non-obvious bits that made it work — keep these

**`export PYTHONNOUSERSITE=1`.** This is the most important line in the file and it is
easy to drop. It stops `~/.local/lib/python3.x/site-packages` leaking into the job, which
is exactly the hazard that produced the hybrid-package problem in v2 locally (two editable
installs both claiming the name `strider`, one pointing at a deleted directory). Without
it a stale user-site package silently shadows the repo.

**`WORK_DIR="${WORK_DIR:-${SLURM_SUBMIT_DIR:-.}}"`.** Makes every script work identically
under `sbatch`, under `srun`, and interactively. Cheap and it removes a whole class of
"works when I run it by hand" confusion.

**`conda activate strider 2>/dev/null || conda activate base`.** Fallback so a job on a
node without the env fails at the *import*, with a readable error, rather than at the
activate with a shell error.

**Echo the resolved inputs at job start.** Every v2 script prints its data paths, config
paths and key parameters before doing anything. When you are reading a six-month-old log
this is the difference between knowing what ran and guessing.

**`set -e`.** A failed conversion stage must not fall through into training on a
half-written dataset.

**Idempotent expensive stages.** The bank build checks `if [ -f "$BANK" ]` and skips.
The header documents how to run it as a separate job when the 12 h wall is tight. Keep
this pattern for v3's data preparation.

**Parameters that were passed explicitly and matter:**
```
--window-half-bins 60
--phase-bins -20,-15,-10,-7,-4,-2,0,2,4,7,11,15,20,30,40,60,80    # 17 edges = 16 bins
--max-windows-per-cell 5000
--feature-catalog configs/onir/onir_v2.yaml
--label-scheme hg2_full
--max-epochs 64
--phase-min -50 --phase-max 100
```
The `--window-half-bins 60` here independently confirms the 60-bin half-window (121-bin
gather), which was mis-stated as 56 in an earlier review draft.

## 3. What to change for v3

### 3.1 Pin the environment

v2 pinned torch and left `numpy pyyaml scipy scikit-learn tensorboard` unpinned. That
alone makes a run non-reproducible six months later.

```bash
# slurm/setup_env.sh
conda create -n strider python=3.11 -y      # NOTE: strider, not strider
conda activate strider
pip install -r slurm/requirements.lock       # generated by `pip freeze` from the blessed env
pip install -e .
```

Use a **new env name** (`strider`). Do not reuse `strider` — v2's env has editable
installs pointing at the v2 tree, and the whole point of the rebuild is not inheriting
that.

### 3.2 One GPU, and fix the QOS mislabelling

Two measured mistakes in v2 worth not repeating:

- `retrain_15class_regular_chain.sh` requested `--gpus=4` with **no DDP anywhere in the codebase** (`grep -E "DistributedDataParallel|torchrun|torch.distributed" training/*.py` returns nothing). That is ~42 idle GPU-hours per 14 h job charged to m4385. The script's own comment says the 4-GPU node was requested for its 256 GB of *host* RAM — a memory problem solved by burning GPU allocation. The v3 sharded loader removes that need.
- `retrain_15class_debug.sh` ran on **`--qos=regular`**, i.e. the script named "debug" did not use debug QOS. Anyone following the naming convention got the opposite of the house rule.

For v3: `smoke.sbatch` **hard-codes** `--qos=debug --time=00:30:00`, and `train.sbatch`
refuses to launch unless a `smoke_passed` marker exists for that config.

### 3.3 Record the environment

v2 recorded nothing — `grep -rl "pip freeze\|git rev-parse\|module list" nersc/` returns
empty, and the shipped checkpoint carries `training_config_hash=''` and
`training_commit='36717bb-dirty'`.

Add a `record_environment(run_dir)` called by every command, writing `environment.json`:
git sha + dirty flag + diff-if-dirty, `pip freeze`, `conda list --explicit`,
`module list`, Slurm job id / node / qos / gpus / cpus-per-task / time limit,
`torch.cuda.get_device_name`, driver and CUDA version, and `ulimit -n`.

### 3.4 Check the torch version question on arrival

Local is torch 2.11; NERSC v2 was 2.5.1. There is an open, cheap and high-value question:

> **Does an all-masked attention row produce NaN on CUDA?**

On CPU it does, in eval mode only. On MPS it does not. If CUDA also NaNs, every v2
validation metric was chance-level, which would reconcile a reported macro-F1 of 0.779
with a bug that should have destroyed it. **Two minutes, first GPU session.** Run it
before anything else — the answer changes how much of v2's reported performance is real.

### 3.5 Data layout differences

| | v2 | v3 |
|---|---|---|
| store | one directory of `.npy.gz` per field, fully loaded into RAM | **sharded** native-bin HDF5 |
| workers | irrelevant (RAM-resident) | benchmark from scratch; lazy per-worker handles guarded on `os.getpid()`; `persistent_workers=True` |
| padding | fixed 64 epochs | variable, pad to batch max |

**Do not copy `num_workers: 0` from the local pilot.** It is a Mac-specific measurement
(548 → 3.4 obj/s from 0 → 12 workers). On Lustre a single reader process will bottleneck.
Cap shards at ~200–500 so the fd budget (`workers × shards touched`) stays inside
`ulimit -n`.

Lustre pass criterion is **metadata ops/sec and job start-up latency**, not throughput.
A million-file dataset can read fast and take twenty minutes to `ls`.

### 3.6 Add exact resume before scaling

v2 has none (`grep -E "resume|optimizer.state_dict|rng_state" training/*.py` → nothing).
Continuation was done by chaining `--init-from-checkpoint` + `--override-epochs`, which
restarts the optimizer, LR schedule (with a fresh warmup), EMA and RNG. **The published
15-class model was produced by such a chain, so its effective learning-rate schedule is
not reconstructible from any config file** — a paper-methods problem, not just an
engineering one.

Gate: train 20 steps → checkpoint → 20 more; separately resume at 20 and train 20.
Assert the two final state dicts and the two next batches are **bit-identical**.

## 3.7 QOS choice — `shared` is the right default for v3, not `regular`

Perlmutter GPU nodes carry 4 A100s. A `regular` job occupies whole nodes, so a
single-GPU trainer on `regular` is billed for hardware it does not use — which is the
same waste as v2's `--gpus=4` request, just less visible. `shared` allows a fractional
node and bills for the fraction.

Since v3 is a **single-process, single-GPU trainer**, `shared` should be the default for
almost everything:

| QOS | use for | why |
|---|---|---|
| **`debug`** | correctness gates ≤30 min: smoke, resume gate, worker parity | fastest queue turnaround. Capped at ~30 min and a small number of concurrent jobs |
| **`shared`** | **development and most training runs** — 15-epoch smokes, scaling tests, parameter arms, and quite possibly the real runs | fractional node, longer walltime than debug, no 2-job cap, and **you are not billed for 3 idle GPUs** |
| `regular` | only if a run genuinely needs a full node (multi-GPU DDP, or host RAM beyond the shared cap) | v3's sharded loader should remove the RAM reason entirely |

*Confirm the current shared-QOS walltime cap and per-GPU memory limit on arrival — these
change. But the shape of the rule holds: do not book a whole node for one GPU.*

## 3.8 v2 timings are not a guide — three reasons

**Do not size v3 jobs from v2's 12 hours.** Three things changed at once and they push in
different directions:

**(a) No warm-started backbone.** v2 initialised from the 11-class backbone's EMA
weights. v3 trains **from scratch**. Expect materially more epochs to converge, and a
different LR schedule — warm-start tolerates a low flat LR, from-scratch wants warmup
plus a higher peak. Note a prior finding that the warm-start *scientific* confound was
≈0 in practice, so nothing is lost by dropping it; it is a wall-clock cost, not a
capability cost.

**(b) Much smaller model.** The v2 backbone was 589,744 parameters; the v3 local pilot
was 19,043. The NERSC model will be larger than the pilot but is unlikely to approach v2.

**(c) Completely different memory and I/O profile.** v2 padded every object to 64 epochs
and held the dataset in RAM — which is why the chain script wanted a 256 GB node. v3 pads
to the batch maximum and streams from sharded HDF5. Peak GPU memory should fall
substantially; host RAM pressure should largely disappear.

**The likely consequence, and it changes what to optimise.** A small model streaming from
Lustre is much more likely to be **I/O-bound than compute-bound**. That inverts the
tuning problem: worker count, shard size and prefetch matter more than anything about the
GPU. It also makes the **GPU-utilisation ≥60% gate the primary diagnostic** rather than a
formality — if utilisation is low, adding GPU hours buys nothing.

Working against that, the finer trial-redshift grid (60 → ~500 points) adds real scan
cost. The scan was ~0.7–3.1 ms against a 17–151 ms encoder forward at 48 trial
redshifts, so an 8× denser grid is affordable but no longer negligible, and it should
appear in the benchmark rather than be assumed.

**Benchmark before booking anything long:**

```
strider benchmark --config <cfg> --data <dataset> \
    --workers 1,2,4,8,16 --steps 200
```

Record, per worker count: examples/sec, **GPU utilisation**, peak GPU memory, host RSS,
open file descriptors, and time per epoch. Then set walltime from measured epoch time ×
planned epochs × 1.5. Until that exists, every v3 walltime is a guess.

## 4. v3 sbatch templates

`slurm/prepare.sbatch` (CPU):
```bash
#SBATCH --account=m4385 --constraint=cpu --qos=regular
#SBATCH --nodes=1 --ntasks=1 --cpus-per-task=32 --time=06:00:00
#SBATCH --output=logs/prepare_%j.out --error=logs/prepare_%j.err
set -e
WORK_DIR="${WORK_DIR:-${SLURM_SUBMIT_DIR:-.}}"; WORK_DIR="$(cd "$WORK_DIR" && pwd)"
eval "$(conda shell.bash hook)"; conda activate strider
cd "$WORK_DIR"; export PYTHONPATH="$WORK_DIR" PYTHONNOUSERSITE=1 PYTHONUNBUFFERED=1
mkdir -p logs
strider prepare --config "$CONFIG" --out "$SCRATCH/strider/data/$DATASET"
```

`slurm/smoke.sbatch` (GPU, debug QOS hard-coded):
```bash
#SBATCH --account=m4385 --constraint=gpu --qos=debug
#SBATCH --nodes=1 --ntasks=1 --gpus=1 --cpus-per-task=10 --time=00:30:00
# ... same preamble ...
strider train --config "$CONFIG" --run-dir "$RUN_DIR" --limit 2000 --epochs 2
touch "$RUN_DIR/smoke_passed"
```

`slurm/train.sbatch` (GPU, **shared** for a 1-GPU trainer, gated):
```bash
#SBATCH --account=m4385 --constraint=gpu --qos=shared
#SBATCH --nodes=1 --ntasks=1 --gpus=1 --cpus-per-task=10 --time=12:00:00
# regular only if a run genuinely needs a whole node - see 3.7.
# Walltime here is a PLACEHOLDER: set it from the measured benchmark (3.8).
# ... same preamble ...
[ -f "$(dirname "$RUN_DIR")/smoke_passed" ] || { echo "no smoke result for this config"; exit 1; }
strider train --config "$CONFIG" --run-dir "$RUN_DIR"
```

## 5. First-session checklist, in order

| # | Step | Why |
|---|---|---|
| 1 | `bash slurm/setup_env.sh` → new `strider` env from the lockfile | reproducibility |
| 2 | `cd $HOME && python -c "import strider; print(strider.__file__)"` | import-origin check; catches user-site shadowing |
| 3 | **The CUDA all-masked-attention test** (2 min, §3.4) | decides how much of v2's reported performance is real |
| 4 | `pytest tests -q` on the cluster | the env, not the code |
| 5 | `strider prepare --limit 10000` → SCRATCH | prints bytes by field |
| 6 | Split + leakage audit; held-out noise construction provably absent from train/select/confirm/cal | any calibration claim depends on it |
| 7 | Storage bake-off: disjoint shards, rotated order, record fd count and Lustre metadata ops/sec | shared caches cannot be cleared |
| 8 | `sbatch slurm/smoke.sbatch` (debug QOS) | anti-uniformity asserted, not just finiteness |
| 9 | Exact-resume gate at `num_workers=8` | bit-identical state dict **and** next batch |
| 10 | Worker parity 0 vs 8 on a ≥2-shard store | the cheapest test for the pilot's 160× slowdown |
| 11 | 15-epoch smoke; **GPU utilisation ≥60%** | below that the data path is the bottleneck — stop and fix before booking regular |
| 12 | First real run, 1 GPU | §9 of the setup plan |

## 7. Things to leave behind

- Unpinned dependency installs
- `--gpus=4` without DDP
- A script named `*_debug.sh` on regular QOS
- `--override-*` CLI flags that change scientific parameters (they appear in a Slurm log and nowhere else)
- Continuation by `--init-from-checkpoint` chaining
- The `strider` conda env name
- Booking a whole `regular` node for a single-GPU job
- Sizing walltime from v2's 12 h - no warm start, smaller model and streaming I/O make it meaningless
